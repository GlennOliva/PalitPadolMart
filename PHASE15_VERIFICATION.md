# Phase 15 — Admin Data Visualization & Report Printing

Phase 15 is the admin-side half of the UI/UX hardening milestone: it turns the
Phase 13/14 admin surfaces into a polished, print-ready dashboard without any
database migration. All data flows through the existing Phase 13 admin RPCs and
Phase 14 analytics RPCs; the client-side additions below are pure presentation
(`@tanstack/charts`, print stylesheets, a report directory page).

## What Phase 15 adds

### Executive dashboard (`/admin`)
- 16 animated KPI cards (revenue, orders, marketplace, moderation) grouped by
  "Performance" quarter-sections, each with a `+/-% Delta` vs the previous
  period, all driven by the existing `admin_analytics_overview`.
- URL-driven date range (`start`/`end`) with auto bucket via `bucketForSpan`
  (≤31d day, ≤180d week, else month) unless `?bucket=` is explicit.
- Three TanStack line charts (gross/net revenue, order volume, growth metrics)
  rendered by `AdminLineChart` over `admin_analytics_timeseries`.
- Top sellers / top categories horizontal bars (`AdminHBarChart`) over the
  Phase 14 ranking RPCs.
- Marketplace status distributions (orders, payments, ratings, disputes +
  refunds) from `getAdminDistributionSnapshots` — all-time counts assembled from
  the admin `listAdmin*` RPCs (`pageSize: 1`), labeled "All-time totals" to
  distinguish them from the period-scoped KPIs.
- "Operational queues" cards (Phase 13 summary) with per-queue drill links.
- `Print Executive Report` — a print-only full report (KPI table, trend table,
  rankings, status tables, footer) rendered as HTML tables for the browser's
  native print dialog.

### Marketplace analytics (`/admin/analytics`)
- The existing Phase 14 page gains the same TanStack line/bar chart treatment,
  a "Status & moderation" section with four horizontal status bars, and a
  `Print Report` action plus a print-only analytics report.

### Report Center (`/admin/report-center`)
- A directory of the 9 printable reports (executive, sales & revenue, orders,
  payments, disputes, refunds, sellers, listings, categories) with `Print Report
  Directory` and a print-only table. Reached from the "Report Center" admin nav
  item. (`/admin/reports` remains the listing-report moderation screen.)

### Shared primitives
- `src/components/reports/` — `ReportHeader` (platform lockup, period,
  generated-at, "Generated by Marketplace administrator", applied filters),
  `PrintReportButton` (labeled, async `onPrepare` → `window.print`, busy state,
  `aria-busy`), `PrintReportTable` (caption heading, repeating thead,
  `break-inside: avoid`, "N rows" footer).
- `src/components/analytics/` — `chart-theme.tsx` (`ADMIN_CHART_COLORS`,
  `chartColorFor`, HTML `AdminChartLegend`), `AdminLineChart`, `AdminHBarChart`,
  `AdminBarChart` — thin wrappers over `@tanstack/charts` 0.18 / react-charts
  with accessible labels; zero-data charts render nothing.
- `src/features/admin/reports/report-utils.ts` — print bounds
  (`PRINT_MAX_ROWS=200`, `PRINT_MAX_PAGES=20`, `PRINT_DEFAULT_PAGE_SIZE=25`) +
  date formatting; `src/features/admin/analytics/admin-distributions.service.ts`
  — all-time status snapshots.
- `src/index.css` — chart chrome, `.print-only`/`.no-print` surfaces, `@media
  print` with `@page { size: A4 portrait; margin: 12mm }`, print tables,
  KPI/queue legend, responsive dashboard grids.

## Known limitations / blockers
- `/admin` charts and the admin print journeys cannot be exercised in-browser
  until the `PHASE13_TEST_ADMIN_*` credential is corrected (currently
  `invalid_credentials`); Phase 15 does not create admin accounts and never
  fabricates PASS for them.
- Chart interactivity is intentionally lightweight: tooltips + animated
  transition, no pan/zoom; screen readers get the HTML legend and table report
  equivalents.

# POST-PHASE-15 — Seller Data Visualization Enhancement

A seller-side UI/UX hardening pass delivered on top of Phase 15. No new
database migration, no new financial formulas, and the same React Charts
architecture already used by the admin UI. Seller identity stays
`auth.uid() → auth_seller_id()` for every analytics RPC; the browser never
supplies — and the analytics APIs never accept — a seller id.

## What the enhancement adds

### Seller dashboard (`/seller`)
- KPI cards grouped by trusted sections (Revenue, Orders & products, Store,
  Engagement, Reviews, Disputes) from `my_seller_analytics_overview`, each with
  a formatted value, an all-time note where the metric is all-time, and a
  previous-period delta where `?compare=1` makes sense. No `NaN`/`Infinity`:
  deltas render `—` (N/A) when the previous figure is missing or 0.
- Sales trend and order trend TanStack **line charts** (`AdminLineChart`) over
  `my_seller_analytics_timeseries` (gross vs net sales; transacted vs completed
  arrivals). Buckets follow the URL `bucket` (day/week/month).
- Top products **horizontal bar chart** (`AdminHBarChart`) over
  `my_seller_analytics_listings` sorted by gross sales, using listing titles
  (never internal UUIDs).
- Order status and customer interest horizontal bars (`AnalyticsHBarList`)
  derived from trusted overview aggregates (transacted/completed/cancelled/
  disputed; views/unique viewers/favorites/inquiries). Views are labeled
  "Listing views" — never "unique" unless uniqueness is actually tracked.
- Customer feedback block (`SellerReviewSummary`) showing the trusted approved
  review count, average rating, and a 5→1 **rating distribution chart**; the
  loading, empty, error, and data states are distinct (see the review bug below).
- **Action items** panel (`SellerActionItems`) — a data-backed "recent seller
  activity" summary built only from overview columns (draft listings, open
  disputes, inquiries this period, no-active-listings warning, or a positive
  "Store is in good shape" message), each linking to the relevant seller screen.
- Date-range filter (`AnalyticsRangeFilter`) + previous-period compare.

### Seller analytics (`/seller/analytics`)
- Full Phase 14 date-range filter, bucket selector, and previous-period compare.
- Sales trend (gross vs net), order trend (transacted/completed/cancelled), and
  order status snapshot line/hbar charts.
- Fulfillment & money summary (completed rate, refunds this period, disputes)
  from trusted overview columns — net sales = gross − completed refunds (Phase
  14 rule, unchanged).
- Top products chart + sortable/paginated listing performance table
  (views/favorites/inquiries/units/gross/rating) from
  `my_seller_analytics_listings`, with CSV export.
- Customer feedback (rating distribution chart + trusted count/average).
- **Print Seller Report** — seller-scoped print-only report (KPI tables,
  period activity, product performance, rating distribution) rendered with the
  Phase 15 `ReportHeader`/`PrintReportTable` primitives. It only ever contains
  the authenticated seller's own data.

## Data sources (all Phase 14, auth-derived)
- `my_seller_analytics_overview` — KPIs, reviews, disputes, fulfillment.
- `my_seller_analytics_timeseries` — sales/order/engagement trends.
- `my_seller_analytics_listings` — per-listing ranking + product table.
- `get_my_seller_rating_summary` / `get_my_seller_rating_distribution` —
  approved-review aggregate + 5→1 distribution (Phase 10 visibility RPCs).
- Historical prices come from the order items/order totals those RPCs read at
  the time of the sale — current listing prices are never substituted.

## Seller isolation
- Every RPC derives the seller from `auth.uid()` via `auth_seller_id()` and
  denies non-sellers (`FORBIDDEN`). There is no default seller on any call, no
  `seller_id` query/localStorage/route trust on the seller analytics surface,
  and RLS/grants from Phases 10–15 are untouched. Forged `?seller_id=…` or
  `localStorage` role spoofs have no effect; multi-seller checkouts stay
  attributed per order `seller_id` exactly as Phase 8 defined.

## Customer reviews summary bug (fixed)
- **Root cause:** the Phase 10 summary RPCs (`listing_review_summary`,
  `seller_review_summary`, `get_my_seller_rating_summary`) are `returns table`
  functions, so PostgREST returns a one-row JSON **array** (e.g.
  `[{ review_count: 41, average_rating: 3.83 }]`). `getMySellerRatingSummary`
  and its two public siblings treated `data` as a single row object, so
  `row.review_count` was always `undefined`, collapsing the summary to
  count 0 / average null. The Seller Reviews page therefore printed
  "No reviews yet" in its Overall Rating header while the review list (a
  different RPC) still showed the real reviews. The unit tests were mocking the
  same wrong wire shape, so they passed while production was broken.
- **Fix:** `readReviewSummaryRow()` in `src/features/reviews/reviews.service.ts`
  reads the first row of the array (tolerating a bare object defensively) and
  returns `null` only when there is genuinely no row. All three summary
  callers now normalize through it.
- **Result (hosted):** the reusable seller account reports `review_count = 41`,
  `average_rating = 3.83`, distribution `{5: 25, 4: 16}` from
  `get_my_seller_rating_summary`/`get_my_seller_rating_distribution`, matching
  `my_seller_analytics_overview.approved_reviews` and the Seller Reviews page
  list. "No reviews yet" now appears only when the trusted approved-review
  count is actually 0.

### Seller analytics timeseries bucket fix (regression)
- A hosted run exposed a Phase 14 RPC bug: `admin_analytics_timeseries` and
  `my_seller_analytics_timeseries` generated bucket timestamps from the exact
  window start and then truncated them, so a month bucket for a
  boundary-spanning window (e.g. 2026-08-18 → 2026-09-16) only produced the
  first month and **silently dropped the trailing month's sales** — the same
  window's overview showed 151 transacted / ₱199,900 but the monthly series
  returned zeros, so the seller analytics line charts legitimately had nothing
  to draw. Fixed in migration
  `20260916000000_phase14_timeseries_bucket_fix.sql` by anchoring the series at
  `date_trunc(p_bucket, v_start)`; day/week buckets keep their exact previous
  output. Hosted check: month buckets now total exactly the overview (151 /
  ₱199,900), guarded by a new `10a` check in `verify-phase14.mjs`
  (boundary-spanning window regression).
